# Migration Strategy

## Schema-less Nature and Implications

CodeSpectra uses the **MongoDB Native Driver** (not Mongoose). This means:

1. **No schema enforcement** — any document can have any fields. TypeScript interfaces in `lib/db/` provide compile-time safety but are NOT enforced at the database level.
2. **String IDs by convention** — All collections use UUIDv4 strings (generated by `crypto.randomUUID()`) instead of MongoDB ObjectIds. This is a deliberate choice so the existing API payloads (which expect string IDs) work without conversion.
3. **String timestamps** — All `created_at`, `updated_at` etc. are ISO-8601 strings (`new Date().toISOString()`), not BSON Date objects. Exception: the Better Auth `user` collection uses native `Date` objects for `createdAt`/`updatedAt`.

### Implications
- **No referential integrity** — Foreign keys are implicit (convention-based naming like `scan_id` → `code_scans.id`). Orphaned references are possible.
- **No migration files** — Schema changes are manual. The codebase has no migration runner.
- **Seed scripts** (`seed-all.ts`, `seed-problems.ts`) are the closest thing to migrations. They check `countDocuments() === 0` to decide whether to insert.

## Rollback Strategy

Since MongoDB has no schema enforcement, **rollback is trivial**: revert the code changes. Data previously written to the old collection name remains accessible by reverting the collection name change in the data layer.

For index changes, use `dropIndex()`:
```javascript
db.code_scans.dropIndex("user_id_1_created_at_-1")
```

## Production Migration Runbook

1. Create a maintenance window (the app has no schema locks, but index creation impacts performance)
2. Run `db.collection.createIndex()` with `{ background: true }` for all new indexes
3. Run the collection rename/fix steps
4. Update the codebase with the fixes above
5. Deploy the updated code
6. Monitor `slowms` query logs for improvement
7. Drop old indexes after 1 week of observation
